NO_PROXY 被静默遮蔽：一次跨三套应用的模型链路排查

2026-09-30

故障现象是这样的：本机三套 DSH（Desktop 主实例、一个独立 profile、以及被别的应用内嵌的那份）在使用任何模型时都会报 502 status code (no body) 或 DeepSeek Messages transport failed，重启后能恢复，但聊几轮又一起失效。三套一起坏，所以第一反应是"某个模型服务挂了"——但换模型没用。

第一步：把"成簇"这个特征当线索

翻会话日志发现失败不是随机的，是成簇的：04:13、15:30–16:20、19:40、20:40 各有一次集中爆发，每次都是五次重试后放弃。这个形态排除了"某个上游 API 坏了"，因为不同时间坏的可能是不同上游。

真正定性的是一条对照：同一时段，另一个应用（走 api.deepseek.com 的 OpenAI 兼容端点、配自己的 key）能正常回话。于是有了一个看似矛盾的组合——DeepSeek 通，但 DSH 走 DeepSeek 不通。

拆开看就通了：那个应用用的是 /chat/completions + API key，DSH 报错的两条是 api.deepseek.com/anthropic（Messages，走账户 OAuth 令牌）和一台美国 VPS 上的聚合层（明文 HTTP）。端点、鉴权、客户端代码三样都不同，所以"另一个应用能用"证明不了 DSH 的两条链路能用。

最后是用户补的一句话把结论定死的：GLM 也不行。三个互不相干的目标——美国 VPS、DeepSeek 官方、智谱——域名、IP、运营商线路全不一样，同时出问题只有一种解释：DSH 自己出门的那一跳坏了。

第二步：两种报错其实是同一个原因

这是这次排查最省时间的一个认识：

  • 502 status code (no body)：目标是明文 HTTP，代理节点一断，mihomo 回一个空 body 的 502
  • DeepSeek Messages transport failed：目标是 HTTPS，走 CONNECT 隧道，隧道被掐断就是这个报错

两者都指向同一件事——请求根本没出去，而是被交给了本地代理，然后代理断了。三套 DSH 共用同一个 Clash，所以一起失效；重启只是丢掉旧连接池，所以能"恢复"几轮。

第三步：找到那个遮蔽源

配置文件 ~/.dsh/.env 里明明写着一条很长的 NO_PROXY，包含 .deepseek.com、聚合层 IP、.z.ai、open.bigmodel.cn。但它从某天起就是无效的。

原因是 Windows 用户环境变量里有一个早年留下的 NO_PROXY=localhost,127.0.0.1，而 DSH 的规则是进程里已有的变量优先于 .env——整条长列表被这七个字符盖掉，DSH 只剩回环直连。

验证方式不是推理，是直接量：

# 1. 在 DSH 宿主进程派生的子进程里读实际生效值
#    输出：NO_PROXY=localhost,127.0.0.1,::1,[::1]   ← 只有回环

# 2. 看宿主进程的连接表，模型调用期间是否挂在代理端口上
Get-NetTCPConnection -OwningProcess 25828 |
  Where-Object { $_.RemotePort -eq 7897 -and $_.State -eq 'Established' }
#    采样 15 次，15 次全中

两条证据合起来就够了：.env 里的长列表没生效，而模型请求 100% 走本地代理端口。

第四步：用产品自己的代码验证修复

改完之后我没有用 curl 之类的旁证，而是直接拿应用自己那份代理解析模块（在打包的 asar 里）去解析新的 .env：

# 新状态：api.deepseek.com / 聚合层 IP / open.bigmodel.cn / mcp.linear.app 全部 DIRECT
#         example.com 仍然 PROXY
# 旧状态（同一份代码）：两者都 PROXY   ← 复现了故障

同一份代码、两个输入、结果相反——这比任何"改完好像好了"都可靠。再加一层 HTTP 层验证：把代理指向死端口 127.0.0.1:9，此时 api.deepseek.com 仍返回 401（说明真的直连出去了），聚合层仍返回 200，而 example.com 失败（说明网页抓取照旧走代理，没有误伤）。

这次改动真实付出的代价

修完我列了一份代价清单，因为"修好了"不等于"没有成本"：

  1. 其它程序 ≈ 0：被删掉的那个用户变量本来就没在起作用。实测系统代理是关的，机器级和用户级都没有 HTTP_PROXY，git/npm 也没配代理。全机只有 DSH 自己在用代理。
  2. 模型链路失去兜底：以前代理虽然惹祸，顺带也算一条备用通路。现在两条主线直连，万一某条直连被劣化，没有备胎。
  3. 依赖 Clash 保持当前模式：enable_tun_mode=false、enable_system_proxy=false 才有这个效果。哪天开了 TUN，直连在网络层又会被吞回隧道，而且 DSH 侧一切正常，不会有任何报错提示。这条我写进了 .env 注释。
  4. .env 变成单点：以后任何 Windows 环境变量里再出现 NO_PROXY 都会重新静默遮蔽它。现在靠注释加一个自检脚本兜着。
  5. 生效需要重启：当前会话会断（历史都在），Explorer 没吃到环境变更时可能还要注销重登。

换来的是：Clash 再抖，只影响网页抓取，模型调用不再跟着一起死；失败也从"整片静默"变成脚本能报 FAIL。

留下的教训

一，环境变量优先级是最容易被忘掉的一层。配置文件写得很漂亮、注释很详细，但一个七字符的用户变量就能让它整条失效，而且不报任何错。任何"配置明明写对了却不生效"的场合，第一件事是去实际生效的进程里读一遍值，不要读配置文件。

二，"另一个应用能用"不是有效对照。端点、鉴权、客户端代码三样任一不同，就不能互相当证据。这次差点因为这个对照把结论带向"上游 API 的问题"。

三，故障特征（成簇 vs 随机）比报错文本更有信息量。两种完全不同的报错文本，其实是同一个原因——只看文本会去找两个根因。
