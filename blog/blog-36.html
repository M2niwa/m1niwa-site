门禁全红但代码没错：沙箱里跑 Godot 的一次假失败

2026-08-26

那天跑完门禁，34 个用例全部失败。我盯着输出目录看了半分钟，每一个 out 文件都是 0 字节，第一个用例还挂了 TIMEOUT。编辑器同时弹了个窗，写着「应用程序错误：指令引用了 0x0058 内存」。这种情况最容易做的错事是去翻最近的改动找回归，我差点就这么干了。

先看失败长什么样

真实的测试失败有几种固定形态，博客 7 那次容器 OOM 复盘里分过好几类。断言不通过，输出里有 expected 和 actual；脚本解析错，有行号和文件名；超时，至少还有半截输出。

这次一个都不是。失败的形式是「没有输出」。0 字节意味着进程在打印任何东西之前就死了，而第一个用例的 TIMEOUT 说明它卡住了一阵才死。再加上那条 signal 11，这个组合指向进程级的环境问题，跟业务逻辑无关。

只改一个变量

我怀疑是写权限。Godot 启动的时候必须写 user:// 目录，具体是 %APPDATA% 下的 app_userdata 和 vulkan 缓存。而当时的执行环境是受限沙箱，只允许写工作区和临时目录，于是做了个只改一个变量的 A/B：

# A：保持真实 %APPDATA%
→ 门禁全红，signal 11

# B：只把 APPDATA 指向临时目录
$env:APPDATA = Join-Path $env:TEMP "godot-appdata"
→ 门禁出 RETREAT_OK，全绿

同一条命令、同一份代码、只改了这一个环境变量，结果完全相反。跟代码没关系，这一点当场就证完了。根因是：Godot 4.7 在写 %APPDATA% 被拒的时候不报错退出，而是直接 SIGSEGV。它连一句「权限不足」都不给，所以从输出侧看就是静默死掉。

三处容易重复出错的

第一，凡是 agent 或脚本启动的 Godot，先改 APPDATA。门禁、探针、编辑器都算。启动编辑器时还要额外设 UV_CACHE_DIR，插件用 uvx 拉 MCP server，uv 缓存默认落在 %LOCALAPPDATA%，同样被拒。这个的症状是 MCP 连不上，不像崩溃，很容易被当成另一个 bug。

第二，编辑器必须挂在常驻后台任务里跑。Start-Process 起 GUI 之后，工具调用一返回就会回收整棵进程树。表现是「编辑器起来 30 秒后连同 uvx、python 一起消失，日志里没有任何崩溃痕迹」。这个和权限问题完全不像，我一开始当成两件事查。

第三，「人跑的」和「agent 代跑的」要分开看。我从资源管理器自己启动编辑器时不受影响，它不过沙箱。所以「我这边能跑」和「你那边跑不了」可以同时为真。攒下来的口诀就一句：见到「门禁全红 + 每份输出 0 字节 + signal 11」，先去查 APPDATA，不要翻代码。

哈希比对那种假红

同一个项目里还有另一种假红，症状毫无相似之处。当时用整文件哈希比对来验证「输出没变」，结果报不相等，但逐行看完全一致。原因是换行符，仓库里是 UTF-8 加 CRLF，某条命令产生的是 LF。用 .NET 的 ReadAllLines 去读会自动识别 BOM 和行尾，行级比对看着正常，但字节数翻倍，Get-FileHash 必然不等。

反过来也有：把 stderr 混进输出再做整文件哈希，也一定假红，因为混进去的是 PowerShell 的报错堆栈，不是内容差异。所以「逐位相同」这个判据要成立，得先钉死三件事：编码、行尾、输出里有没有夹带别的东西。

被假红藏起来的真问题

假红最麻烦的地方在于它会把真问题藏起来。这个项目里发生过一次。一位协作者改探针脚本时，插入函数体的编辑第一次就失败了（工具要求先 read 再 edit），但他只把调用点改上了，函数体没补。整个文件引用了不存在的函数，编译失败。

而当时的门禁不编译 tools 目录。探针脚本属于工具目录，不在测试范围内。于是所有探针「表面能跑、数据全零」，看起来像「这轮改动没有效果」，实际是测量工具根本没启动。

这个缺陷最后是被 0 字节的输出暴露的。一个测量脚本输出 0 字节，只可能是它自己坏了，不可能是被测对象恰好等于零。之后把工具目录的语法冒烟也接进了门禁。

这套东西和 NO_PROXY 那次排查里「自证不等于他证」是同一条线。输出为空比输出为错更值得怀疑自己；一个判据要成立，得先把它的前提钉死；门禁的盲区比门禁的失败更贵，因为失败会被人看到，盲区不会。
