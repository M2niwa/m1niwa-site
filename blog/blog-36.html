门禁全红但代码没错：沙箱里跑 Godot 的一次假失败

2026-08-26

一个 34 个用例的 Godot 测试门禁，跑完显示全部失败。逐个看输出文件——每一个都是 0 字节，第一个用例还超时。编辑器同时弹出"应用程序错误：指令引用了 0x…0058 内存"。这种场面最容易做的错事，是开始翻最近的代码改动找回归。

先看现象的形状，别先看代码

真实的测试失败有几种典型形态：断言不通过（输出里有 expected / actual）、脚本解析错（有行号和文件名）、超时（有部分输出）。这次一个都不是——失败是"没有输出"。0 字节意味着进程在打印任何东西之前就死了。

而第一个用例的 TIMEOUT 说明它不是立刻死的，是卡住之后才死。加上那条 signal 11（SIGSEGV）的崩溃提示，这个组合指向的不是逻辑错误，是进程级的环境问题。

A/B 定位：只改一个变量

怀疑对象是写权限。Godot 启动时必须写 user:// 目录——具体是 %APPDATA%\Godot\app_userdata\<项目>\logs 和 vulkan\*.cache。而当时的执行环境是受限沙箱，只允许写工作区和临时目录。

于是做一次只改一个变量的 A/B：

# A：保持真实 %APPDATA%
$env:APPDATA 不变 → 门禁全红，signal 11

# B：只把 APPDATA 指向临时目录
$env:APPDATA = Join-Path $env:TEMP "godot-appdata"
→ 门禁出 RETREAT_OK，全绿

同一条命令、同一份代码、只改了这一个环境变量，结果完全相反。与代码无关，已证。

根因也很清楚：Godot 4.7 在写 %APPDATA% 被拒的时候不报错退出，而是直接 SIGSEGV。它连一句"权限不足"都不给，所以从输出侧看就是"静默死掉"。

三条会重复踩的处置

1. 凡是 agent 或脚本启动的 Godot，先改 APPDATA。门禁、探针、编辑器都算。启动编辑器时还要额外设 UV_CACHE_DIR——插件用 uvx 拉 MCP server，uv 缓存默认落在 %LOCALAPPDATA%，同样被拒，症状是 MCP 连不上而不是崩溃。

2. 编辑器必须挂在常驻后台任务里跑。Start-Process 起 GUI 之后，工具调用一返回就会回收整棵进程树——表现是"编辑器起来 30 秒后连同 uvx/python 一起消失，日志里没有任何崩溃痕迹"。这个症状和权限问题完全不像，很容易被当成两个 bug。

3. "人跑的"和"agent 代跑的"必须分开看。用户从资源管理器亲自启动的编辑器不受影响（不过沙箱），所以"我这边能跑"和"你那边跑不了"可以同时为真。

省时间的判别口径

攒下来的口诀就一句：见到"门禁全红 + 每份输出都是 0 字节 + signal 11"，先去查 APPDATA，不要翻代码找回归。

这条口诀的价值不在于省了多少分钟，而在于它把"假红"和"真红"分开了。分不开的时候，人会做两件坏事：改本来正确的代码，以及不信任本来有效的测试。

同类的第二种假红：哈希比对

这个项目里还有一个形态完全不同的假红，值得并列记着。当时用整文件哈希比对来验证"输出没变"，结果报不相等，但逐行看完全一致。原因是换行符——仓库里的文件是 UTF-8 + CRLF，而某条命令产生的输出是 LF。用 .NET ReadAllLines 去读会自动识别 BOM 和行尾，行级比对看着完全正常，但字节数翻倍、Get-FileHash 必然不等。

反过来也有坑：2>&1 把 stderr 混进输出再做整文件哈希，也一定是假红——因为混进去的是 PowerShell 的报错堆栈，不是内容差异。

所以"逐位相同"这个判据要成立，前提是先钉死三件事：编码、行尾、以及输出里有没有夹带别的东西。否则验证本身比被测对象更容易出错。

最值钱的一次：假红掩盖了真红

假红最危险的地方不是浪费一轮排查，而是它会把真问题藏起来。这个项目里就发生过一次：一位协作者在改一个探针脚本时，插入函数体的编辑第一次就失败了（工具要求先 read 再 edit），但他只把调用点改上了，函数体没补。结果整个文件引用了不存在的函数，编译失败。

而当时的门禁不编译 tools/**——探针脚本属于工具目录，不在测试范围内。于是所有探针"表面能跑、数据全零"，看起来像"这轮改动没有效果"，实际是"测量工具根本没启动"。

这个缺陷最后是被 0 字节的输出暴露的：一个测量脚本输出 0 字节，只可能是它自己坏了，不可能是被测对象恰好等于零。之后把工具目录的语法冒烟也接进了门禁。

三条通用规则

一，输出为空比输出为错更值得怀疑自己。断言失败是信息，0 字节是"信息通道断了"。先确认通道，再读内容。

二，一个判据要成立，得先把它的前提钉死。整文件哈希、逐位相同、行级 diff——每一个都有自己的一套前提（编码、行尾、夹带内容）。不写清前提的验证方法，等于没有验证。

三，门禁的盲区比门禁的失败更贵。失败会被人看到，盲区不会。这个项目后来补了两类盲区：工具目录的语法、以及场景实例化的冒烟。补上之后，那个"探针从不启动"的缺陷立刻被抓住了。
